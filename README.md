# ShowroomBot

Windows-приложение для выполнения YAML-сценариев в 1С через RDP и проверки локального Outlook.
Для сборки нужен .NET 10 SDK. Для распознавания интерфейса нужны
русский или английский компоненты OCR Windows.

## Локальная настройка

В PowerShell из каталога проекта:

```powershell
Copy-Item configexample.yaml config.yaml
New-Item -ItemType Directory -Force Scenarios
Copy-Item Examples/ScenarioReference.example.yaml Scenarios/Scenario1.yaml
```

Заполните `config.yaml` своими параметрами VPN/RDP, а
`Scenarios/Scenario1.yaml` — параметрами базы и учётными данными 1С.
Если рабочие файлы уже существуют, сохраните свои настройки перед копированием.

```powershell
dotnet build
dotnet run
```

Аварийная остановка сценария: **Ctrl+Alt+F12**.
Логи, screenshots и результаты OCR сохраняются в `diagnostics` рядом с исполняемым файлом. При запуске удаляются файлы старше одного дня.
Во время выполнения UI показывает имя текущего шага и краткую последнюю запись из `scenario.log`; статус обновляется не чаще одного раза в 3 секунды.

`OpenConfig` открывает RDP на полный экран, проверяет текущее окно и перебирает
остальные через Alt+Tab (не более 15 окон). Если конфигуратор не найден, запускает
команду CONFIG через Win+R и ждёт подтверждения интерфейса. Параметры
`executable`, `server`, `database`, `user`, `password` задаются прямо в OpenConfig.
В локальном сценарии 2 они скопированы из Open1C. Каждая проверка окна записывается
в лог со снимком экрана. Перед ReadCode добавьте OpenConfig.

`ReadCode` работает с активным конфигуратором и сначала проверяет видимый узел «Общие модули» и его дочерние строки.
Если категории не видны, он возвращается к корню через Home и раскрывает «Общие»;
поиск категорий ограничен четырьмя попытками и 60 секундами. Уже раскрытый список
не прокручивается ради повторного поиска родителя. Дерево распознаётся отдельно
от остального экрана, с допуском небольших ошибок OCR в названиях категорий.
Выбор и открытие модуля также ограничены 60 секундами и максимум 12 прокрутками
(меньшие настроенные лимиты сохраняются). В `scenario.log` записываются искомый
узел, найденные строки, причины прокрутки и подтверждение редактора модуля;
снимки дерева и OCR имеют суффиксы `.tree.png` и `.tree.toolkit-ocr.txt`.

Открытие модуля подтверждается совпадением заголовка либо появлением редактора с процедурами/функциями. Если редактор уже был открыт, появление других имён в `VisibleRoutines` также подтверждает открытие при плохом OCR заголовка, без ожидания таймаута. Последующее чтение и закрытие принимают такое подтверждение. Идентификатор модуля — выбранная строка дерева; для длинных заголовков допуск OCR составляет примерно 12% длины (минимум 2 ошибки).

После открытия модуля выполняется визуальное чтение в течение `readDurationSeconds: 43`: переходы к видимым процедурам/функциям, раскрытие «+», движения мыши и прокрутка. Текст не копируется, буфер обмена не нужен. Обязательный параметр YAML `ReadModuleCount: 3` задаёт количество разных модулей за шаг, а время чтения применяется к каждому. После каждого модуля выполняется Ctrl+F4. После короткого чтения бот ищет другую процедуру крупными прокрутками с преимущественным движением вниз. Для первого модуля используется случайный буквенный якорь из списка: `ак`, `вс`, `зак`, `зап`, `об`, `обе`, `пер`, `пос`, `рас`, `ск`, `ста`, `уп`, `фо`, `ртк`. Якорь вводится без пауз между буквами, затем выбирается случайный видимый модуль. Для следующего модуля: 50% — другой случайный якорь, 50% — соседний модуль в текущей области. Если непосещённых соседей нет, прокручивается дерево метаданных, преимущественно вниз. Посещённые модули повторно не открываются. Если модулей или попыток не хватило, шаг завершается ошибкой. Пустые модули и модули без исходного текста пропускаются. `minimumCodeLines` сохранён для совместимости YAML и больше не влияет на чтение.

## Запросы Infostart Toolkit

Справочник всех шагов: `Examples/ScenarioReference.example.yaml`. Скопируйте
его под новым именем в `Scenarios`, заполните параметры запуска базы и цвет её
панели. Команда открытия: `Infostart Toolkit` → `Консоль запросов`.
Шаг `Open1C` автоматически открывает RDP по адресу из `config.yaml`, используя
тот же механизм, что кнопка «Открыть RDP», или активирует существующее окно.
Шаг ожидает окно удалённого сеанса без открытых диалогов подключения
и пять секунд устойчивого фокуса перед продолжением. Ожидание ограничено
60 секундами и поддерживает отмену. Проверка окна и фокуса не подтверждает
завершение загрузки всех программ на удалённом рабочем столе.
После запуска новой базы `Open1C` по умолчанию ожидает её интерфейс до
7 минут (`readyTimeoutSeconds: 420`), проверяя screenshot каждые 30 секунд
(`pollIntervalMs: 30000`). При обнаружении клиента сценарий сразу продолжается.
Сначала шаг `Open1C` находит или запускает базу, затем `ExecuteToolkitQuery`
открывает консоль и выполняет запрос в уже активной 1С. Параметры запуска,
учётные данные и настройки поиска окна задаются только в `Open1C`.

`queryFile` разрешается относительно каталога приложения. Запросы в UTF-8
хранятся в `Queries1c`; все `Queries1c/**/*.txt` копируются при сборке
и публикации. Для второго запроса добавьте файл с понятным названием и
укажите его путь в следующем шаге — изменения C# не требуются.
Содержимое файла проверяется до действий в интерфейсе. Способ ввода задаётся
в шаге: `queryInputMode: paste` — вставка, `queryInputMode: typing` — набор
(по умолчанию для сценариев без настройки). В справочнике указан режим typing по умолчанию. Для вставки включите передачу
буфера обмена в mstsc: текст проверяется обратным копированием из редактора,
при несовпадении запуск отменяется; прежний локальный буфер восстанавливается.
`queryInputTimeoutSeconds` ограничивает время вставки и проверки.
В режиме `typing` запрос набирается
посимвольно с клавиатуры: Ctrl+A и Backspace очищают редактор, кириллица
передаётся Unicode-событиями, переносы — клавишей Enter. Автоматические отступы редактора сохраняются: дополнительные пробелы допустимы в запросе, а удаление строки после Enter может повредить текст. Буфер обмена при наборе не используется. Если после `typing` 1С сообщает ошибку запроса, шаг один раз очищает редактор, вставляет исходный текст через `paste` с обратной проверкой и повторяет выполнение. Для этого нужна передача буфера обмена в mstsc. Ошибка после повторной вставки останавливает шаг.
Параметры набора для всего приложения задаются в `config.yaml` → `automation.typing`.
`minimumDelayMilliseconds: 80` сохраняет прежнюю максимальную скорость локальных
сценариев: задержка никогда не бывает меньше этого значения. Темп плавно
меняется участками (`tempoSegmentCharacters`, `slowdownFactor`), добавляются
случайные задержки (`jitterMilliseconds`) и редкие паузы
(`pauseProbability`, `pauseMinimumMilliseconds`, `pauseMaximumMilliseconds`).
Параметр `typingDelayMs` удалён из шагов и примеров.
Для длинных запросов лимит автоматически увеличивается с учётом длины и максимальных задержек;
queryInputTimeoutSeconds задаёт минимальный лимит. При таймауте ввод останавливается
без запуска. Обратного сравнения текста с файлом при клавиатурном вводе нет.

Общий механизм мыши использует `automation.mouse`: прежние
`movementDurationMilliseconds` и `stepDelayMilliseconds`, кривизну
`curvatureRatio`, небольшие отклонения `deviationPixels` и случайное изменение
длительности `durationVariation`. Скорость плавно увеличивается и уменьшается,
последняя точка всегда совпадает с целью. Все шаги, включая составной Toolkit,
используют общие методы `SendTextAsync` и `MoveToAsync`; собственных скоростей нет.
Вставка (`queryInputMode: paste`) остаётся доступной и не эмулирует набор.

Комментарии к параметрам есть в `configexample.yaml` и локальном `config.yaml`.
Сохранение меняет значения в существующем YAML, сохраняя комментарии и неизвестные
ключи. Ошибка чтения YAML не заменяет файл значениями по умолчанию.
Изменения поведения применяются после перезапуска приложения. Отмена и
Ctrl+Alt+F12 прерывают также случайные паузы и перемещения.

Все задержки, таймауты и интервалы шагов необязательны; значения по умолчанию
заданы в `ScenarioStepDefinition`. Рабочие файлы в `Scenarios` не содержат
параметров времени и комментариев. Полный комментированный справочник всех
всех типов шагов — `Examples/ScenarioReference.example.yaml`.

Значения по умолчанию для ожиданий: `consoleTimeoutSeconds: 30`, `queryInputTimeoutSeconds: 20`, `queryTimeoutSeconds: 120`,
`pollIntervalMs: 500`, `resultStablePolls: 3`. Они регулируют ожидание результата до прокрутки.

Скорость прокрутки задаётся в YAML шага `ExecuteToolkitQuery` одним параметром:

```yaml
scrollSpeed: 5
```

Целое число от 1 (медленно) до 10 (быстро). По умолчанию — 5: прежний темп normal,
2 деления колеса и пауза 700 мс. На 1 — 1 деление / 1500 мс, на 10 — 10 / 100 мс.
Из скорости рассчитываются только `scrollNotches` (деления колеса за попытку)
и `scrollPauseMs` (пауза перед screenshot/OCR). Эти два поля в YAML не используются.
Старые fast/normal/slow замените на 10/5/1.
Для быстрого теста укажите `scrollSpeed: 10`, для медленного рабочего показа — `scrollSpeed: 1`.
Фактический темп зависит также от RDP/OCR и отпускания Ctrl (150 мс).
Повторное движение мыши и пауза наведения до 200 мс нужны только при изменении позиции курсора.

Защитные параметры задаются отдельно и не меняются при изменении скорости:

| Параметр YAML | Default | Назначение |
|---|---:|---|
| `maxScrollAttempts` | 300 | Максимальное число отправок колеса |
| `scrollTimeoutSeconds` | 660 | Общий лимит времени, включая наведение, паузы и OCR, с |
| `scrollUnchangedAttempts` | 4 | Число попыток подряд без изменений для остановки, минимум 2 |

Конец таблицы по положению ползунка завершает прокрутку сразу. Если большая таблица
вообще не реагировала на колесо, серия неизменных кадров приводит к ошибке.
Для длинной таблицы при медленном показе можно отдельно увеличить бюджет времени.
При исчерпании лимитов шаг успешен, неполная прокрутка записывается в журнал.
Ошибки запроса и отмена сценария по-прежнему прерывают шаг.
Области находятся по русскому Windows OCR и рамкам элементов; для Toolkit
нужен установленный русский компонент OCR Windows.

Прежний результат принимается только после наблюдаемого выполнения,
изменения результата, количества строк или показателя времени выполнения.
Если очень быстрый повторный запрос даёт полностью идентичную таблицу и то же
время, а состояние выполнения не попало в снимки, шаг остановится по таймауту
с диагностикой: достоверно подтвердить новый запуск по этим кадрам нельзя.
Снимки и OCR могут содержать текст запроса и данные результата.

Автоматические проверки без RDP:

```powershell
dotnet run --project Tests/ShowroomBot.Checks.csproj
```

В реальном RDP проверьте повторное использование и запуск клиента, открытие
консоли, кириллицу и переносы в редакторе, быстрый/долгий запрос, ошибку и
пустой результат, прокрутку при разных размерах окна и положении разделителя,
отмену и Ctrl+Alt+F12 во время ввода, ожидания и прокрутки.

## CheckMail: локальный Outlook

Минимальный сценарий проверки почты:

```yaml
name: "Проверка почты"
steps:
  - type: CheckMail
```

Контекст определяется типом шага: `Open1C`, `OpenConfig`, `Open1CSection`, `Open1CCommand`
и `ExecuteToolkitQuery` выполняются в RDP; `CheckMail` — на машине ShowroomBot;
`Wait` не переключает окна. Указывать `local/rdp` в YAML не нужно. Сценарий
только из локальных шагов и пауз можно запускать автоматически без готового VPN/RDP.
В смешанном сценарии следующий шаг 1С снова активирует удалённое окно штатным способом.

Перед `CheckMail` окна сеансов RDP сворачиваются без отключения. Шаг использует
запущенный классический Outlook в текущем сеансе Windows. Если его нет, запускается
`C:\Program Files\Microsoft Office\root\Office16\OUTLOOK.EXE /embedding`.
Если процесс уже есть, повторный запуск не выполняется. Главное окно не открывается
и не активируется. Ожидание COM ограничено 60 секундами; занятый COM повторяется
до 30 секунд.
Если `GetActiveObject` не находит объект в ROT, через 3 секунды при наличии локального
процесса выполняется резервная COM-активация `Outlook.Application`, которая подключается
к текущему экземпляру Outlook. Способ подключения и HRESULT ошибки записываются в журнал.
Outlook и ShowroomBot должны работать от одного пользователя с одинаковыми правами.
Профиль Outlook должен быть настроен; окна входа, выбора профиля и разрешений
программного доступа нужно закрыть/обработать вручную. Новый Outlook (`olk.exe`)
этим шагом не поддерживается. Вызов COM, заблокированный самим Outlook диалогом,
может задержать отмену до закрытия диалога; после возврата отмена проверяется.

Через Outlook Object Model открываются «Входящие» основного профиля и выбираются
`MailItem` с `UnRead = true`. Подпапки и дополнительные ящики не обходятся.
Отправитель, тема и полный обычный текст `Body` читаются непосредственно через COM;
вложения не отправляются. Для этого не используются OCR, screenshots, RDP-координаты
или удалённый ввод. Письма не открываются и `UnRead` не изменяется. Чтение выполняется
через объект папки без переключения текущей папки, изменения выделения, области
чтения или сохранения представлений Outlook.

Непрочитанные письма, ещё не отправленные ботом, передаются через `TelegramBotService`
в личный чат `telegram.allowedUserId`. Длинный текст разбивается на сообщения без
обрезки. Шаг ожидает подтверждения отправки всех частей каждого письма и только
потом сохраняет его в историю. Флаг `telegram.notifyDemoEvents` на отправку почты
не влияет. Если новых писем нет, шаг успешно завершается даже при выключенном
Telegram; если новые есть, но Telegram выключен или доставка не удалась, шаг
завершается ошибкой, а неотправленное письмо остаётся доступным для следующей попытки.

История: `%LOCALAPPDATA%\ShowroomBot\mail-delivery-history.json`.
Ключ — пара `StoreID + EntryID`; в файле хранятся только идентификаторы и время
успешной отправки UTC. История общая для сценариев данного пользователя Windows,
сохраняется после перезапуска/пересборки и не зависит от очистки диагностики.
При каждом `CheckMail` записи старше 5 дней удаляются; давно отправленное письмо,
которое всё ещё непрочитано, после этого может быть отправлено снова. Перемещение
между хранилищами Outlook также может изменить идентификатор и привести к повтору.
Файл обновляется через временный файл с заменой; блокировка предотвращает
одновременную обработку почты двумя экземплярами бота. Повреждённая история
останавливает шаг, чтобы не переслать всю почту заново.

Между Telegram и локальным файлом нет общей транзакции: при аварийном завершении
после доставки, но до записи истории, либо при неоднозначном сетевом сбое возможен
повтор. Если не удалось отправить одну из частей длинного письма, следующая попытка
отправит письмо целиком. Прочитанность Outlook во всех случаях остаётся состоянием
пользователя, а не подтверждением доставки бота.

Проверка на рабочей машине: закрытый и уже открытый Outlook, пустые «Входящие»,
одно новое непрочитанное письмо, повторный запуск и перезапуск ShowroomBot,
ошибка Telegram, длинное письмо, отмена, переход `1С → CheckMail → 1С`.
Убедитесь, что письмо остаётся непрочитанным, а повторный запуск его не отправляет.
Автоматические проверки используют подставной Outlook и HTTP-транспорт без
чтения реального ящика и отправки реальных сообщений.

## Telegram

Telegram работает внутри приложения через long polling [Telegram Bot API](https://core.telegram.org/bots/api).
Входящие порты, webhook и отдельный сервер не нужны. Создайте бота через
`@BotFather`, затем заполните **локальный** `config.yaml` рядом с исполняемым файлом:

```yaml
telegram:
  enabled: true
  botToken: '' # Здесь локально укажите выданный токен.
  allowedUserId: 0 # Здесь укажите свой числовой Telegram user ID.
```

В исходниках для запуска через `dotnet run` настройте локальный `config.yaml`
в корне проекта: он копируется при сборке. Реальные токен и ID не добавляйте
в `configexample.yaml` или Git. По умолчанию Telegram выключен; старые конфиги
без этой секции продолжают работать. Пустой/некорректный токен или ID ≤ 0
отключают polling. Настройки применяются после перезапуска.

Команды принимаются только от `allowedUserId` в личном чате с ботом.
Сообщения других пользователей и групп игнорируются.

- `/start` или `/menu` — справка и кнопочное меню: запуск/остановка демонстрации,
  скриншот, статус, автозапуск и подключение VPN. В меню автозапуска можно включить
  или выключить его и выбрать бездействие 5, 10, 15, 30 или 60 минут; кнопка
  «Другой интервал» подсказывает команду `/idle N`. Текстовые команды также работают.
- `/status` — состояние демонстрации, выбранный сценарий, текущее состояние VPN,
  последний результат проверки доступности RDP и настройки автозапуска, включая время.
- `/vpn` — запуск подключения первого VPN из `vpn.connectionNames` текущей конфигурации
  через Windows RAS API. Профиль и сохранённые учётные данные должны быть настроены
  в Windows для пользователя ShowroomBot. Новые настройки VPN не создаются.
  Бот получает сохранённые логин и ссылку на пароль через `RasGetCredentials` и передаёт
  их в `RasDial`. Пароль не извлекается в открытом виде и не передаётся в командной строке.
  Телефонная книга и настройки профиля не изменяются. Если данные не сохранены,
  команда просит выполнить ручное подключение с сохранением логина и пароля в Windows.
  Ответ подтверждает только запуск команды подключения; авторизацию на телефоне
  пользователь подтверждает самостоятельно. Фактическое соединение проверяется
  существующим детектором VPN и отображается в `/status`. Команда не ждёт подтверждения
  на телефоне и не блокирует обработку остальных команд Telegram.
- `/demo` — запуск сценария, выбранного в окне ShowroomBot, тем же механизмом,
  что кнопка запуска. Ответ подтверждает начало запуска, а не успешное завершение
  сценария. Результат выполнения придёт отдельным уведомлением.
- `/stop` — запрос штатной отмены текущего сценария, в том числе запущенного из UI
  или автоматически. Настройку автозапуска команда не меняет.
- `/autostart on` / `/autostart off` — включить или выключить автозапуск.
- `/autostart status` (или `/autostart`) — текущее состояние и интервал бездействия.
- `/idle N` — интервал бездействия от 1 до 1440 целых минут, например `/idle 15`.
  Сам по себе интервал не включает автозапуск. Изменения обновляют UI и сохраняются
  в существующих `autoStartDemo` и `idleMinutes` через штатное сохранение настроек.
- `/screenshot` — весь локальный рабочий стол, включая все мониторы, PNG-файлом
  без сжатия Telegram. Окна не активируются; снимок показывает то, что видно локально,
  и может содержать конфиденциальные данные. Нужен доступный интерактивный рабочий стол
  Windows; при блокировке/отключённом сеансе захват может не работать.

В отдельном блоке «Telegram» на форме флажок «Присылать уведомления о демонстрации»
включает или отключает уведомления о запуске, завершении, ошибке и остановке.
Изменение действует сразу и сохраняется в `telegram.notifyDemoEvents`.
Для старых конфигов уведомления по умолчанию включены. Команды бота, включая
`/screenshot`, работают независимо от этого флажка.

При включённых уведомлениях для любого запуска (UI, автоматически или `/demo`) бот отправляет название сценария.
При успешном завершении, ошибке или остановке отправляет результат и снимок текущего
экрана; при ошибке — также её текст. Снимок делается сразу при завершении без активации
RDP, до показа диалога ошибки, и сохраняется в диагностике сценария. Если захват
недоступен, результат всё равно отправляется с пояснением об отсутствии снимка.
Уведомления отправляются последовательно в фоне и не задерживают сценарий или `/stop`.
Ошибки доставки записываются в `scenario.log`, не меняя результат сценария;
повторной отправки уведомлений после сетевой ошибки или перезапуска нет.

Скрытие окна в трей сохраняет polling; «Выход» останавливает его и отменяет
сетевые запросы. Сетевые ошибки не завершают приложение: повторная попытка —
через 5 секунд. Токен, HTTP-ошибки и тела ответов не журналируются.
При каждом запуске polling удаляет webhook и накопленные команды, чтобы
старый `/demo` не запустился после перезапуска. Используйте отдельного бота
для ShowroomBot и только один экземпляр приложения с этим токеном.
Временный снимок команды `/screenshot` удаляется после попытки отправки;
снимки уведомлений остаются в диагностике и удаляются её штатной очисткой.

## Публикация исходников

В Git публикуются `configexample.yaml` и `Examples/ScenarioReference.example.yaml`
с вымышленными значениями. Рабочие `config.yaml`, `Scenarios/*.yaml`,
диагностика и результаты сборки исключены через `.gitignore`.
Не добавляйте локальные настройки принудительно через `git add -f`.

Исключение файла из Git не удаляет его из прежних коммитов. Если в истории
уже были реальные данные, для новой публичной публикации используйте очищенный
снимок исходников без старой папки `.git` и создайте новую историю репозитория.
